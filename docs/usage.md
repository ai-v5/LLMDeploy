# 本机 token 统计

`deploy_usage` 是固定 vLLM 版本的 Stat Logger 插件；不增加网络监听，不依赖网关、Windows 或通知服务。每个 API 进程独立保存 SQLite WAL，按秒聚合其实际收到的引擎统计增量，查询时汇总所有 DP 和 API 进程。数据目录须挂载到宿主机并长期保留，不能随容器删除。

## 启用与查询

在既有渲染命令增加 `--usage`。生成器仍不执行部署；显式启动时注册本仓插件，写入宿主机 `artifacts_dir/usage`，代码和元数据通过 `PYTHONPATH` 加载，不需要联网或安装依赖。每次启动产生独立运行标识，默认配方期望 8 个 API 进程；手工改变 `--api-server-count` 时必须同步 `LLMDEPLOY_USAGE_WRITERS`。

```sh
python3 scripts/render.py --host local/host.json --output local/run.sh --usage
python3 -m deploy_usage.report --root /srv/artifacts/usage
```

启用需要重建容器，按通知文档先暂停告警，保留旧容器与配置，验证后恢复。固定模型、镜像和两个源码补丁不变。普通重启只产生新账本，不重置累计值；回退到未启用插件的容器期间不记账，会体现为未覆盖时间。

## 口径与边界

| 项目 | 定义 |
| --- | --- |
| 输入 | 与 `vllm:prompt_tokens_total` 相同，包含每次请求的历史上下文及图片 token；在引擎前端收到相应 prefill 统计时计入 |
| 输出 | 与 `vllm:generation_tokens_total` 相同，包含推理过程、首 token 和中止前已观测到的输出，不保证客户端收到 |
| 缓存 | 与 `vllm:prompt_tokens_cached_total` 相同，前缀 KV 命中与外部 KV 传输之和；已包含在输入中，不是 Engram 或图片预处理缓存 |
| 均速 | 窗口输出 / 窗口墙钟秒数，包含空闲及未覆盖时间；今天为零点至查询时刻，累计为首次记账至查询时刻 |
| 生成速度 | 已结束请求的 `sum(max(output-1,0)) / sum(decode_seconds)`，是按解码时间加权的请求速度，不能当作并发总吞吐；请求跨日时该项归入结束所在窗口 |

今天按北京时间零点切分；24 小时、3 天、7 天分别为滚动 24/72/168 小时。输入、输出及缓存按统计事件时间归属，边界精度 1 秒；报表不含尚未结束的当前秒。累计覆盖所有保留的账本。历史请求、原始 token、回答正文、请求 ID 和凭据均不保存。

回调只向容量为 4096 的队列非阻塞入队，独立线程写盘并每约 5 秒更新心跳。心跳只证明记录器在对应时间段工作。缺失 API 记录器、心跳超过 30 秒、队满、数据库损坏和写入失败均不能宣称完整；查询显示起点、截止时间和未覆盖时长，未知不当作零。记账故障不向推理抛出异常；数据丢失或损坏时应保留现状并恢复存储，不能删除账本后沿用旧累计。

SQLite 使用 WAL / NORMAL；已提交记录可跨普通进程退出保留，正常退出限时排空队列，异常退出可能丢失队列尾部，断电还可能丢失最近事务。引擎产生但前端尚未消费的输出，也可能遗漏。因此这是持续运行的用量统计，**不是可保证故障下逐 token 零丢失的计费账本**，也无法补齐启用前的历史。升级需要重新核验统计接口、与 Prometheus 增量一致性、8 个记录器及存储失败行为。

## 小鲁班状态

在私有通知配置的 `usage` 对象中，以既有节点端口为键配置 `target`（已有 SSH 信任的目标）、`code_dir`（本仓代码所在目录）、`data_dir`（宿主机账本目录）。示例结构：

```json
{"usage":{"19001":{"target":"example-primary","code_dir":"/srv/LLMDeploy","data_dir":"/srv/artifacts/usage"},"19002":{"target":"example-backup","code_dir":"/srv/LLMDeploy","data_dir":"/srv/artifacts/usage"}}}
```

通知进程每约 30 秒在后台通过 SSH 只读查询，两台分别超时，查询不会阻塞健康观察。仅允许固定报告命令、已验证的路径与目标；远端结果仅提取有界数字，原始文本和异常不进入消息。以通知机本地接收时间判断缓存是否超过 90 秒，避免跨机时钟偏差造成误判。事件与窗口仍按部署机时间；与通知机的估计偏差超过 5 秒时显示提示，不自动修改系统时钟。

`@小鲁班 状态` 保留部署数量和健康状态，并按实例返回五个窗口的输入、输出、缓存、命中率、均速和生成速度。IP 仍只显示最后一段；查询游标、投递去重及失败不自动重发的合同不变。统计故障不等同于 vLLM 故障。

## 统一入口的 IP 用量与本机页面

**进程内采集候选仍在隔离验证，未经现场切换审查不要启用。** 候选在既有认证网关内观察已写出的响应，不另加 HTTP 转发跳；不改变原请求认证、后端选择或响应内容。采集记录器启动失败时网关按原路径运行，页面应显示采集失联；网关启动失败时记录器必须结束，避免空心跳。网关的拒绝体排空单独限制为最多 480 个在途连接、每连接最多 128 MiB 和 30 秒，超限或排空器无法接收时回到原关闭行为，不保证所有过载响应完整。切换前必须验证两个网关和监督进程的实际源码、端口及状态文件归属，由调用方暂停新请求，等待包括慢上传和排队在内的已接受请求全部结束后再关闭准入；否则关闭准入也可能拒绝已接受的请求。切换过程中仍可能短暂返回 502 或 503。Windows 独占绑定仅防止同地址监听冲突，不替代对全部监听地址、PID 和已接受连接的检查。原有入口如另有独立网关，需要分别验证和切换。

进程内候选从 Caddy 默认生成的单值 `X-Forwarded-For` 获取直接对端 IP，忽略客户端可自行提供的 `X-LLMDeploy-Client-IP`。仅在已核实 Caddy 未配置可信代理、未改写此头并确由该 Caddy 转发的入口上使用；配置变化须重新验证。头缺失、多值或非法时显示未知。Caddy 前还有其他代理时，显示的是其直接对端而非自动追溯最终客户端；本机进程直接连接网关时可以伪造该头，不能把来源 IP 当作安全身份。

候选的 32 MiB 限制是**保留原始采集缓冲**的合计，不是进程 RSS 上限；JSON 解码与 Python 对象会额外占用内存。单个事件或 JSON 响应超过 4 MiB、事件 data 行超过 4096、JSON 结构或转义工作超过保护上限，以及捕获资源不足时，相关统计保守显示未知，不影响原响应。超过 64 KiB 且未发现符合协议的最终用量候选的 SSE 事件可跳过解析：它会清除此前用量；只有之后重新观察到有效的协议结束用量及结束标记，才计量该请求。跳过之前若尚未确认首增量，首增量等待和速度也显示未知。此口径验证最终用量和结束顺序，不保证跳过的正文事件可解析；后端或协议版本变化时须重新核验。速度与原有账本一样是入口估算，不是引擎阶段实测。

`deploy_stats` 是独立的入口统计组件，适用于固定 DeepInfer recipe API 的 Chat Completions、Responses 和 Messages JSON/SSE。设计上它放在 Caddy 与**现有认证网关之间**，转发请求和响应，从正常结束的原生 `usage` 提取输入、输出及缓存命中。页面和采集代理都只监听 `127.0.0.1`。这是与上面的 vLLM Stat Logger 分开的账本，不能把两者直接相加，也不自动补齐启用前的历史。

**当前入口代理尚未通过部署审查，不要接入真实流量。** Windows 上，在请求体较大、网关延迟拒绝且未读取完整请求体时，连接复位可能导致错误响应正文截断。固定等待或预读不能保证保留未收到的字节。必须先修复并验证拒绝端关闭行为，或改用不增加此 HTTP 跳转的采集方式，再重新审查真实入口切换。

Chat Completions 的最终流式用量语义来自[固定版本的 recipe 源码](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/deepseek-recipe/src/protocol/openai/chat_completion/response/chunk_generator.rs)；更换后端或协议版本时须重新核对，不按旧版本假设填零。

页面展示今天、滚动 24 小时、7 天和累计的总 Token、输入、输出、缓存命中、窗口输出 tok/s 与各请求 IP；另有最近 24 小时和近 14 日的统计。**总 Token = 输入 + 输出**，缓存命中是输入子集。窗口输出 tok/s 为已计量输出 / 窗口墙钟秒数，包含空闲时间，不是单请求解码速度。所有 Token 按请求完成时间入桶；24 小时曲线显示完整的 10 分钟区间，左侧 24 小时汇总包含未满区间。这不是逐 token 生成时刻的曲线，长请求在结束前没有最终用量。

24 小时曲线展示输入和输出 Token、平均请求缓存命中率以及设备 Prefill 和 Decode 采样吞吐。每个区间的平均请求命中率是各已计量请求的 `缓存输入 / 输入` 的算术平均，输入为零的请求不计入；这与概览中 `缓存输入之和 / 输入之和` 的加权命中率不同。命中率汇总按请求数加权；设备吞吐曲线的计算和覆盖边界见下文。无可测样本显示未知；覆盖有缺口时均值仅代表已观测样本，不是全部请求的下限。

左侧导航分别打开用量概览、当前连接、会话记录、请求来源、每日用量和后端状态；窄屏时导航显示在页面顶部。当前连接、会话汇总、请求记录、请求来源和每日用量分别支持每页 10、20 或 50 条，默认每页 20 条；点击表头可切换升序和降序。会话及请求在完整结果上排序后分页，未知值排在已知值之后。翻页时保留查询快照，避免新请求导致重复或漏行；会话和请求任一不在首页时共用同一快照。请求来源和每日用量在非首页时分别保留自身快照；概览和当前连接页每约 2 秒通过只读轻量接口查询当前连接，连接随采样变化，翻页结果可能变动；失联或快照超过 3 秒时显示未知并回到第一页。顶部刷新会回到首页并获取新快照；后端状态表支持排序。

页面同时展示当前在途推理请求、可判定请求成功率和可见请求速率、入口观测的首个可见增量与代理内耗时 p95，以及按网关身份口径分组的会话汇总和逐请求记录。成功率只以已计量成功、明确失败和中断的请求为分母；结果未知的请求被排除，因此不是全部请求的成功率。指标选择参考 [vLLM 生产指标](https://docs.vllm.ai/en/latest/usage/metrics/)与 [NVIDIA 推理指标定义](https://docs.nvidia.com/nim/benchmarking/llm/metrics)。采集进程每秒把内存中的当前在途集合写成快照；快照超过 3 秒或心跳失联时显示未知。列表只覆盖经过本代理且请求头已识别的推理连接；客户端绕行、入口回退和切换前的连接不在其中。后端通常只在响应结束时提供用量，进行中的输入、输出、命中率和速度为未知而非零。

新采集的会话依次使用 `x-session-affinity`、`x-deepseek-harness-session-id`、`x-session-id`，以及 JSON 的 `prompt_cache_key` 或首条用户内容，按网关的认证主体和身份规则计算哈希指纹。指纹不是加密：知道同一 API key 的人仍可能通过候选内容比对低熵输入，账本和页面必须限制访问。请求体只在内存中短暂处理，不写入账本或日志；原始字节缓冲单请求最多 1 MiB、全进程合计最多 32 MiB，JSON 解码和规范化还会产生额外临时内存。超限、请求体完整识别之前中断或无有效身份时显示未知；请求体已识别后取消，仍可能保留会话指纹。由首条用户内容推导的身份与网关一样只是近似：不同会话的首条内容相同或历史被压缩时可能合并或变化。历史上未识别的会话由于未保存请求体，无法回填。会话汇总只包含可识别会话，未计量用量及覆盖缺口显示为下限；命中率只针对已计量请求。页面可翻页查看各会话和请求，不保存原始会话标识或请求正文。

当前后端没有导出逐请求引擎 prefill 或 decode 时间。对有非空文本、推理或工具增量的 SSE，代理可观测从入口接收请求到首个可见增量的时间，以及从首个增量到响应结束的时间；前者包含上传、排队、网络和首输出等，后者包含流式输出和响应收尾。页面提供（输入−缓存命中）/首增量等待、（输出−1）/首增量后时长及两段时间占比作为**入口估算**；首个增量可能包含多个 Token，后者不等于精确 decode tok/s。会话汇总的时间是可观测请求时间之和，并发时不能当作会话墙钟时间。非流式、没有可见增量或终止用量缺失时相关值显示未知。p50/p95 为窗口内可用样本的线性插值，不代表未覆盖请求。

会话汇总的 Prefill、Decode 入口估算分别是可测成功请求的未命中输入或输出减一之和，除以相应入口时间之和，按请求耗时加权而非并发总吞吐；总览首增量等待为可测成功请求的算术平均。Prefill 速度排除等待时间为零的样本，Decode 速度排除输出不超过 1 或后段时间为零的样本。缓存命中率为已计量请求的缓存输入之和 / 输入之和。无可测样本时显示未知。

总览可选接入独立的只读引擎和设备采集器。每个实例只有同一日志 step 收齐全部配置的 DP rank、阶段一致、设备映射正确且步速差和日志时间差在界限内时，才展示各 rank 当前步速率之和；这是日志采样近似，不是严格共同墙钟窗口的精确总吞吐。默认跨设备组视图仅相加有有效样本的实例，忽略缺失组并展示有效组数和配置组数，全部缺失时显示“—”；也可选择单个实例。各组并非同时测量，采样时间范围含误差超过 30 秒时显示跨度。跨组 Prefill-MFU 以有效组的设备峰值算力加权，驱动 HBM 百分比以有效组的设备数加权，不将百分比直接相加。日志时间是写出时间而非执行时间，异步队列可能延迟，且日志不包含 worker 启动标识；因此不能证明所展示 step 与当前工作进程的实时执行严格对应。推测解码和未暴露的回退路径均可能造成偏差，Decode 计数不保证等于客户端收到的 Token。

Prefill-MFU 采用上述 Prefill 采样吞吐乘以操作者配置的模型 FLOP/token，除以对应设备理论峰值之和，仍为模型假设下的阶段估算，不是硬件 FLOP 实测；未经明确计入的 Attention 等计算不包含在内。设备 HBM 带宽百分比来自驱动的设备级采样，可能包含其他工作负载或混合阶段；目前没有可验证的 Decode 阶段带宽归因，因此 Decode-MBU 显示未知，而不把设备整体带宽冒充纯 Decode。表格中的阶段步耗时来自引擎 CPU 计时日志及其有效 rank，包含调度等开销，不是每请求 GPU/NPU kernel 耗时。

采集器通过 SSH 只读获取严格数值化的引擎日志摘要和 DCMI 设备读数，不保存或向本机返回原始日志、请求内容或认证信息。需在私有配置中绑定后端端口、容器、rank 与设备映射、已核验的引擎源码与 native 哈希、镜像指纹和 DCMI 库哈希，以及模型 FLOP/token 和设备理论峰值；模型、版本或映射变化后应重新核对。SSH 使用现有密钥或代理，配置不放密码、密钥或其他凭据；机器标识和实际配置只放被忽略的私有目录。

[采集配置示例](../hosts/telemetry.example.json)中的模型参数和哈希均为占位值，不能用于真实估算。复制并核验私有配置后，可用 `python -m deploy_stats.telemetry --config <私有配置> --once` 做单次只读预检；持续采集使用 `--port` 指定 loopback 端口，看板通过 `dashboard --telemetry-port <端口>` 读取该采集器。可另用 `--history-database <私有 SQLite 路径>` 保存设备采样历史。每个完整的 10 分钟桶只取已收到的各步速率采样均值，不是该桶 Token 数除以墙钟时长；跨组显示有样本组的同桶采样均值之和，并标出每桶有效组数，采样时刻不一定重合。空心点和虚线表示部分组缺失。跨组曲线的 24 小时数字是有采样的桶均值，覆盖组数可能随桶变化；单组则按采样数加权。全部缺失的桶留空，启用前的设备历史无法补齐。配置或主机身份变化后只展示当前身份的历史；文件不会自动删除旧记录，需自行监控磁盘空间。存储缓慢或不可用时实时采样继续运行，但历史采样可能缺失。入口用量曲线仍来自入口账本。

这些数字仅来自客户端最终响应中可解析的用量。认证网关可能在响应头发出前重试另一后端；前一次失败尝试即使已经消耗 Token，也不会出现在最终响应的用量中，入口采集器无法感知或补计。取消或中断的请求也可能已在后端消耗 Token。因此，即使采集覆盖和可见响应完整，这些数值也不是后端物理总消耗或计费账本。

请求中断、上游错误、未知协议、缺失或互相矛盾的用量字段记为未计量，不当成零。Chat 流的用量后若再出现其他数据事件，或 Messages 流的用量后再出现非 `message_stop` 事件，先前快照不再视为最终用量；只有随后再次收到有效用量并正常结束，才计量该请求。无采集覆盖显示空缺；`≥` 表示已观测下限，命中率仅针对已计量请求。统计通过异步队列写盘，页面只展示已提交数据，可能滞后于请求完成。队列满时记录丢失数并将相关采集运行周期视为不完整；运行周期与心跳用于标识中断，队列丢失数可能包含所选窗口以外的时间。采集进程失联或异常退出而未正常排空时，其运行周期内的统计也保守标为不完整，因为上次心跳前仍可能存在未写盘事件。SQLite 使用 WAL / NORMAL，异常退出或断电可能丢失尾部；这不是故障下逐 token 零丢失的计费账本。

页面的运行覆盖只反映采集进程心跳，不证明 Caddy 已经切换或所有入口流量均经过该代理。启动代理但尚未切换、入口配置后来变化或客户端绕过入口时，仍可能有未记录流量；必须单独核验真实入口路由，不能将心跳 100% 当作入口完整性证明。示例配置将原认证网关作为回退入口：采集代理的连接失败或其他往返网络错误可能触发被动健康标记，使随后新请求暂时绕过采集器。回退期间的请求不会记入账本，即使采集进程随后恢复也无法补计。

采集代理最多同时处理 480 个连接；Windows 下分派到三个独立事件循环，超限时尝试返回 429 并标记统计缺口。对于带请求体的请求，代理在转发请求体前会等待上游提前返回的认证或准入拒绝：4 KiB 以下最多约 10ms，4 KiB 及以上最多约 100ms。Windows 定时器精度可能使等待提前结束，固定等待不能消除所有拒绝与上传之间的 TCP 竞态。上线前必须核对连接上限不低于实际网关需要的并发与等待配额，并实测对首输出延迟的影响；扩大服务池后需重新评估，不能把连接数当作模型吞吐能力。

账本只保留 IP、不可逆会话指纹、请求时间、HTTP 状态及数值用量，不保存认证信息、原始会话 ID、提示词、模型回答或原始 Token。IP、指纹和账本属于私有运行数据，目录需限制本机访问，只放忽略的 `local/` 或操作者自己的私有位置。旧版账本首次由采集器打开时会原地迁移并保留历史；旧记录没有阶段时间和会话指纹。页面拒绝跨站 Origin 和非 loopback Host，且不提供修改接口；同一台机器上有权限读取账本的用户仍可读取这些 IP。

可选 `--backend-port` 指定本机回环地址上的 DeepInfer 原生 `/metrics` 端口，每个端口单独读取运行数、排队数、存活 worker、接入状态、累计输入和累计缓存命中。后端不可达、计数缺项或累计值不一致时显示未知；累计数按各后端进程生命周期统计，重启会重置。当前接口没有 KV 占用、设备利用率或逐请求引擎阶段时延，不以估算代替。

## Motor 与 vLLM 指标

Motor 部署可在现有网关命令中增加 `--statistics-database <私有账本>`，将响应观察器装入网关进程；不修改客户端请求、流内容或上游认证。账本打开失败时网关仍提供服务，采集不可用。只在 Caddy 已验证覆盖客户端转发地址且网关确为入口目标时，来源 IP 才有入口侧的可信来源；直接访问网关的客户端不享有该保证。实际流量是否经过已装配的网关仍需在上线后独立核验，采集器心跳不能证明入口接线。

看板以 `dashboard --database <同一账本> --motor-management-port <管理端口> [--motor-management-port <管理端口>] --motor-history-database <新的私有历史文件>` 运行；Motor 模式不能同时使用旧的 `--backend-port` 或 `--telemetry-port`。管理端口必须通过本机回环隧道连接可信的 Motor 管理服务。看板每约 30 秒只读 `/instances` 和已注册 worker 的 `/metrics`，最多四个并发 worker 请求；采样前后核对实例角色、端点和就绪状态，管理端不一致、采样期间拓扑变化、worker 缺失或计数重置时保守标记部分或未知。两次拓扑读取一致仍不能证明整个间隔内没有发生过变化。速率按相同进程和相同指标序列的相邻计数差 / 墙钟间隔计算：Prefill 取本地实际计算输入，Decode 取生成 Token；两阶段不相加作为请求总量。后端计数的范围可能包含其他入口。

通过导出进程启动时间和计数回退识别重启，但不能保证发现导出进程未退出的所有内部引擎重启。真实阶段耗时仅为 vLLM 相邻采样间请求阶段直方图的聚合均值，不是单会话时间。Prefix Cache 命中率按 Prefill 侧 Token 加权，不能替代入口每请求命中率的算术平均，也不把 Decode 的跨实例 KV 传输当作用户前缀复用。历史文件按十分钟保存速率采样均值，仅显示当前实例身份的历史；历史开始之前、采集故障和 worker 变化期间不补造数据。当前未采集到可归因的 NPU 阶段算力和 HBM 流量，Prefill-MFU、Decode-MBU 和 HBM 利用率保持未知。

Motor 模式只用新网关进程记录的来源标记判断当前采集心跳，旧采集器的心跳不会冒充现网心跳。心跳覆盖不证明入口路由覆盖，因此该模式下总量均标为已观测下限；历史账本继续保留，未能验证的时段不宣称完整。如果最终响应提供输入和输出但没有缓存明细，仅记录这两项并标为部分用量；缓存命中率的分母只包含有缓存明细的请求。流式响应未提供最终用量时请求标记为未计量，不能从引擎聚合计数反推每 IP 或会话的用量。

Motor 模式使用版本化的 v5 页面资源和接口；旧版页面继续轮询旧接口时会显示统计不可用，而不会把新计数器按旧日志口径展示。切换后用户需要刷新看板标签页。

下面是**待单独授权部署**时的示例；目录、端口和原网关地址须先核实，命令不会由开发或测试自动执行：

```powershell
New-Item -ItemType Directory -Path local/stats -Force
python -m deploy_stats proxy --port 19882 --upstream-port 19010 --database local/stats/usage.sqlite3
python -m deploy_stats dashboard --port 19881 --database local/stats/usage.sqlite3 --backend-port 19001 --backend-port 19002
```

示例中的 `19010` 仅代表既有网关的 loopback 端口。[Caddy 示例](../services/deepinfer/Caddyfile.stats.example)仅供审阅。先在隔离环境验证代理，再按维护流程核实入口及现有连接，将 Caddy 的 `reverse_proxy` 首选目标改为 `127.0.0.1:19882`，连接失败时回退到同一个既有认证网关，并在该反代块内设置：

```caddyfile
header_up X-LLMDeploy-Client-IP {remote_host}
```

Caddy 必须覆盖客户端传入的同名头；采集器不信任客户端的 `X-Forwarded-For`，缺失、重复或非法来源显示为“未知来源”。`{remote_host}` 是 Caddy 的直接对端：若 Caddy 前还有其他代理，显示的是该代理 IP，需先明确可信代理链，不能自行相信转发头。回退只在尚未连接采集代理时重试 POST；不要配置会在已连接后重放 POST 的 `lb_retry_match`，不要对认证入口配置无凭据的主动健康探测。参见 Caddy 的[负载均衡与重试说明](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#load-balancing)、[反向代理头部说明](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers)和[请求占位符](https://caddyserver.com/docs/caddyfile/concepts#placeholders)。所有入口别名须采用相同配置，直接回退网关的请求不在统计范围。

切换前保留原 Caddy 配置，验证认证失败控制、JSON/SSE 字节内容、并发、取消、大请求、来源 IP 和页面；核对源版本与真实用量字段，检查记录器心跳及缺失数。验证通过才恢复通知。回退时把 Caddy 的目标恢复到原网关，保留账本并停止本次采集/页面进程；回退期间形成统计空缺，不得视为零。上述均需另行授权，离线测试和合成预览不构成实际部署或真机验收。
